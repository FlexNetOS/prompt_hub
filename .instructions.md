# Copilot Instructions for prompt_hub

This file provides custom instructions for GitHub Copilot and other AI agents working in this repository.

## Project Overview

**prompt_hub** is a Rust monorepo containing three crates:
- **prompt-hub**: Core library with database, search, auth, audit, and advanced AI features
- **prompthub**: CLI binary for managing prompts
- **prompthub-server**: HTTP API server with OpenAPI documentation

**Tech Stack**: Rust 2024 Edition, MSRV 1.91.1, libsql (SQLite-compatible), FTS5 full-text search, vector embeddings

**Key Constraint**: `#![forbid(unsafe_code)]` — No unsafe Rust allowed anywhere.

## Code Organization

### Module Structure

```
prompt-hub/src/
├── models.rs          # All type definitions (Prompt, Agent, etc.)
├── error.rs           # HubError enum and error handling
├── lib.rs             # Module exports and public API
├── hub.rs             # Core PromptHub coordinator
├── storage.rs         # libsql database operations
├── search.rs          # FTS5 and vector search
├── auth.rs            # RBAC and authorization
├── audit.rs           # Audit logging
├── lock.rs            # Distributed locks with TTL
├── templates.rs       # Handlebars template rendering
├── vibe.rs            # Vibe Coding engine
├── evolution.rs       # Genetic algorithm for prompt optimization
├── privacy.rs         # Privacy scanning for secrets/PII
├── confidence.rs      # Confidence scoring
└── [20+ more modules]
```

### Dependency Rules (CRITICAL)

1. **models.rs and error.rs are the foundation** — every other module depends on them
2. **hub.rs is the orchestrator** — it owns all module instances but no module imports hub
3. **No circular dependencies** — enforced by the module structure
4. **Feature flags** — defined in `prompt-hub/Cargo.toml` only (never in workspace Cargo.toml)
5. **Async throughout** — All I/O operations are async/await, no blocking code

## Coding Standards

### Rust Style

- **Edition**: 2024
- **MSRV**: 1.91.1 — Test with `cargo +1.91.1 check`
- **Formatting**: `cargo fmt --all`
- **Linting**: `cargo clippy --all-targets --all-features`
- **No unsafe**: `#![forbid(unsafe_code)]` is non-negotiable
- **Error handling**: Use `thiserror` derive macros, never `.unwrap()` in production code
- **Testing**: Write tests in the same file with `#[cfg(test)]` modules

### File Structure Template

```rust
//! Brief module description
//!
//! Longer explanation if needed.

use crate::error::HubError;
use crate::models::*;

pub struct YourType { /* ... */ }

impl YourType {
    pub async fn your_method(&self) -> Result<Output, HubError> {
        // implementation
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[tokio::test]
    async fn test_something() {
        // test
    }
}
```

### Type Naming

- **Struct**: PascalCase (`PromptHub`, `LockManager`)
- **Enum**: PascalCase (`HubError`, `Action`)
- **Function**: snake_case (`create_prompt`, `search_similar`)
- **Constant**: SCREAMING_SNAKE_CASE (`MAX_RETRIES`, `DEFAULT_TIMEOUT`)
- **Private fields**: Prefix with `_` if intentionally unused

## Database & Migrations

- **Database**: libsql (SQLite-compatible)
- **Migrations**: SQL files in `migrations/` numbered sequentially
- **Schema**: Check `migrations/0001_initial.sql` for the base schema
- **Transactions**: Use explicit transactions for multi-step operations
- **Constraints**: Primary keys, foreign keys, and unique constraints required

## Testing

- **Unit tests**: In the same file as the code, in `#[cfg(test)]` modules
- **Integration tests**: In `tests/` directory
- **Benchmarks**: In `benches/` directory using Criterion
- **Run all**: `cargo test --all-features`
- **Run specific**: `cargo test --lib auth::`
- **Bench**: `cargo bench`

## Common Tasks

### Add a new feature to the hub

1. Add types to `models.rs`
2. Add error variants to `error.rs` (if needed)
3. Implement storage layer in `storage.rs`
4. Implement the feature in a new module (e.g., `myfeature.rs`)
5. Export from `lib.rs` and integrate into `hub.rs`
6. Add tests at each layer
7. Update `SPEC.md` if it's a user-facing feature

### Fix a compilation error

1. Check `plan.md` for known blockers and fixes
2. Search for the symbol in the codebase using Copilot's search
3. Verify all imports are correct (`use crate::...`)
4. Check type mismatches against `models.rs`
5. Run `cargo check` to verify the fix

### Update the database schema

1. Create a new migration file in `migrations/` (e.g., `0010_my_change.sql`)
2. Update `storage.rs` to use the new schema
3. Update `models.rs` if struct definitions changed
4. Add a test in `storage.rs` to verify the migration works
5. Document the change in `CHANGELOG.md`

### Add a new HTTP endpoint

1. Define request/response types in `models.rs`
2. Add the handler in `prompthub-server/src/routes.rs`
3. Update `prompthub-server/src/openapi.rs` with the endpoint definition
4. Add middleware integration in `prompthub-server/src/middleware.rs` if needed
5. Add integration tests in `tests/`

## Performance Considerations

- **Search**: FTS5 is optimized for text queries; use FAST mode for most searches
- **Vectors**: Embeddings stored as `BLOB`, indexed with cosine similarity
- **Locks**: TTL prevents deadlocks; heartbeat extends locks automatically
- **Caching**: In-memory caches in `sync.rs` with invalidation on writes
- **Batch operations**: Use transactions for multi-step operations

## Security

- **Auth**: AgentIdentity with RBAC capabilities in `auth.rs`
- **Audit**: Every mutation logged in `audit.rs` with immutable evidence
- **Sanitization**: Prompt injection detection in `sanitize.rs`
- **Privacy**: PII/secret detection in `privacy.rs`
- **No hardcoded secrets**: Use config files with environment variable substitution
